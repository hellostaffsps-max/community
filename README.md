# مجتمع Goat Journey

تطبيق عربي باتجاه RTL لمشاركة وصفات المشروبات، يبدأ بالقهوة والمجتمع الفلسطيني. الهوية والألوان الحالية معالجة مؤقتة قابلة للمراجعة، وليست شعارًا رسميًا معتمدًا. التطبيق مستقل عن Lab وAcademy وDesk.

## نطاق النسخة

حسابات وتأكيد بريد واستعادة كلمة المرور؛ ملفات عامة بلا بريد إلكتروني؛ وصفات ومسودات ومكونات وخطوات وصورة؛ بحث وفلاتر؛ محفوظات خاصة؛ تعليقات؛ بلاغات ومراجعة وإخفاء مع سجل إجراءات. حقول جرعة البن والماء والناتج والحرارة والوقت اختيارية. لا توجد بيانات وهمية في صفحات المنتج. عند تعذر قاعدة البيانات تظهر حالة تعذر واضحة.

## التشغيل المحلي

يلزم Node.js 22 أو أحدث، وnpm. على Windows استخدم `npm.cmd` إذا منع PowerShell تشغيل `npm.ps1`.

```powershell
npm.cmd ci
Copy-Item .env.example .env.local
npm.cmd run dev
```

افتح `http://127.0.0.1:3000`. أدخل القيم العامة الصحيحة في `.env.local` محليًا، ولا ترسل أسرارًا في المحادثة. الملف مستثنى من Git. وضع التطوير يتصل بالمشروع المحدد إن كانت قيمه موجودة؛ عمليات الواجهة تكتب بيانات حقيقية، وليست محاكاة.

| المتغير | الاستخدام |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | عنوان مشروع community المحدد أو Supabase المحلي في التطوير |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | المفتاح القابل للنشر فقط، بصيغة `sb_publishable_…` للمشروع السحابي |
| `APP_ORIGIN` | أصل التطبيق بلا مسار ولا شرطة أخيرة؛ HTTPS عند الإطلاق |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | مفتاح Turnstile العام عند تجهيز التسجيل |
| `ALLOW_PUBLIC_SIGNUP` | يبقى `false` حتى اختبار SMTP والتحقق الأمني؛ ثم `true` |

المفتاح السري لـTurnstile، إن أُعد، مكانه إعداد CAPTCHA في Supabase Auth؛ لا يضاف إلى ملفات المتصفح. التسجيل مغلق في التطبيق وفي Supabase Auth حاليًا؛ تم حفظ تعطيل التسجيل المباشر والتحقق من `disable_signup=true` عبر إعدادات Auth العامة. تأكيد البريد مفعّل، والدخول المجهول معطل.

## قاعدة البيانات

المصدر المقروء `supabase/schema.sql`، والنسخة التنفيذية `supabase/migrations/20261115000204_community_foundation.sql`. يوجد اختبار يمنع اختلافهما. أنشئت migration بواسطة Supabase CLI. هي تهيئة أولى مرة واحدة وليست سكربتًا لحذف وإعادة إنشاء قاعدة موجودة. يحفظ CLI تاريخ التطبيق، فلا يُعاد تنفيذ migration مطبقة.

عند توفر Docker يمكن تشغيل بيئة Supabase محلية كاملة:

```powershell
npm.cmd run db:start
# بعد ضبط .env.local لقيم البيئة المحلية وتشغيل migration عبر CLI:
npx.cmd supabase db reset --local
```

`db reset --local` يمسح قاعدة التطوير المحلية فقط. لا تستخدمه على بيانات مطلوبة. أدوات SMTP المحلية تعرض رسائل الاختبار دون إرسالها إلى بريد حقيقي. Docker غير متاح في البيئة التي أُنشئ فيها هذا المشروع؛ لذلك اختبارات RLS تستخدم PostgreSQL داخل PGlite ولا تدّعي اختبار خدمات Supabase كاملة.

طُبّقت التهيئة السحابية بالفعل عبر SQL Editor داخل `community` في معاملة واحدة، بعد الموافقة والتحقق أن المشروع فارغ. لا تُعد تنفيذها. تم التحقق من 11 جدولًا محميًا بـRLS وحاويتين خاصتين ومنع الزائر من حفظ الوصفات. لا يوجد سكربت يمنح أي مستخدم دور مشرف تلقائيًا.

لم يتوفر اتصال CLI مخول بالمشروع الصحيح؛ لذلك لا يوجد حتى الآن سجل `supabase_migrations.schema_migrations` على السحابة. قبل أول `db push` لاحق، اربط CLI بالمشروع المحدد عبر تسجيل آمن، وطابق المخطط ثم سجّل migration الحالية كمطبّقة باستخدام `supabase migration repair 20261115000204 --status applied --linked`. لا تحاول حل فرق التاريخ بإعادة إنشاء الجداول. منح دور المشرف يحتاج تحديد المستخدم والموافقة عليه عبر قناة إدارية موثوقة.

## الأمان

- RLS على الجداول المكشوفة. القراءة العامة للوصفات المنشورة غير المخفية فقط، مع استثناء صاحب المحتوى وصلاحية مراجعة البلاغ المحددة. المسودات لا يقرأها المشرف لمجرد كونه مشرفًا.
- الصور في حاويتين خاصتين؛ سياسة القراءة تتبع الوصفة. واجهة `/api/media` تستخدم جلسة صاحب الطلب، ولا تستعمل تجاوزًا إداريًا أو روابط عامة للمسودات.
- أذونات صريحة، ملكية غير قابلة للتغيير، وعدم الثقة في role من metadata. الملفات العامة لا تحتوي البريد. المحفوظات خاصة حتى بالنسبة للمشرف.
- حفظ الوصفة ومكوناتها وخطواتها في معاملة واحدة، مع رقم إصدار يمنع الكتابة فوق تعديل أحدث. لا يمكن نشر وصفة بلا مكوّن وخطوة، حتى عبر Data API.
- تحقق Zod على الخادم، قيود SQL، فحص Origin للطلبات المعدّلة، حد لحجم الجسم حتى مع streaming، وأسماء عشوائية للصور. صور JPG/PNG/WebP فقط مع فحص ترويسة المحتوى وحد حجم؛ الفحص ليس فك ترميز كاملًا للصورة ولا مضاد فيروسات.
- حدود قاعدة البيانات: 20 وصفة/يوم، 30 تعليقًا/ساعة، 60 تعديلًا/ساعة، 10 بلاغات/يوم، 120 حفظًا/ساعة، 50 رفع صورة/يوم. التخزين يحد عدد الملفات لكل وصفة/ملف شخصي إلى 3 لتقييد الملفات اليتيمة.
- صفحات الجلسة وبيانات الصور دون cache. لا يُخزّن HTML المصادق عليه في CDN. السجلات تحتوي رمز خطأ ومعرّف طلب فقط، دون المحتوى أو البريد أو المفاتيح.

## Cloudflare وربط GitHub

مسار Next.js المحلي باقٍ للمقارنة. أضيف مسار vinext الذي توصي به وثائق Cloudflare الحديثة لهذا النوع من المشاريع؛ حالته Beta. يعتمد القرار النهائي على نجاح بناء Worker واختبار جلسات Auth ورفع الصور فعليًا. OpenNext بديل عند ظهور عدم توافق. لا يستخدم التطبيق ISR أو تحسين الصور، ولا ينشئ KV أو R2 أو Images أو خدمة إضافية.

- `vite.config.ts`: إعداد App Router على Workers.
- `cloudflare.config.ts`: Worker اسمه `community`، ومدخل vinext، وStatic Assets فقط.
- `npm run build:vinext`: يبني محليًا.
- `npm run start:vinext`: معاينة Worker محليًا.
- أمر النشر يتطلب مراجعة وموافقة منفصلة؛ وجوده لا يعني أنه نُفّذ.

للمعاينة على المنفذ 4173، أنشئ `.env.production.local` (مستثنى من Git) بالقيم `APP_ORIGIN=http://127.0.0.1:4173` و`ALLOW_PUBLIC_SIGNUP=false`، ثم شغّل `npm run build:vinext` و`npm run start:vinext -- --host 127.0.0.1 --port 4173`. قيم `NEXT_PUBLIC_*` تُثبّت أثناء البناء. يقرأ `cloudflare.config.ts` متغيري `APP_ORIGIN` و`ALLOW_PUBLIC_SIGNUP` من بيئة البناء ويضيفهما كـtext bindings إلى Worker؛ غيّر الأصل إلى العنوان الإنتاجي المعتمد قبل بناء إصدار النشر. يرفض التطبيق أي Origin خارجي غير HTTPS، ويسمح HTTP لعناوين loopback المحلية فقط. يفحص `typecheck` ملفات المصدر عبر `tsconfig.check.json` دون مخرجات المسارات المتعارضة بين Next.js وvinext؛ بناء Next.js يفحص أنواع مساراته المولّدة.

المستودع العام الذي اختير فارغ عند الفحص. Worker متصل به مسبقًا والنشر الآلي على رفع الكود مفعّل، لذلك رفع الكود قد يطلق نشرًا عامًا. لا تدفع تغييرات قبل اعتماد النشر وإعداد build/deploy commands ومتغيرات البيئة الصحيحة. فشل آخر CI موجود قبل عملنا عند جلب المستودع، وليس نتيجة اختبار هذا الكود.

## الدومين والبريد والإطلاق

اختيرت خطة Cloudflare Free بموافقة المستخدم. حُفظت خوادم `lilyana.ns.cloudflare.com` و`sid.ns.cloudflare.com` في Hostinger بموافقة منفصلة. آخر حالة مرصودة: Cloudflare ينتظر انتشار خوادم الأسماء. حُفظت أهداف سجلّي `@` و`www` الحالية؛ لم يُربط Worker بالدومين ولم يُنشر التطبيق.

قبل الإطلاق يلزم اعتماد عنوان التطبيق النهائي، ثم ضبط Site URL وقائمة Redirect URLs الدقيقة في Supabase (`/auth/callback`)، وإعداد SMTP مناسب واختبار رسائل التأكيد والاستعادة، وإعداد Turnstile في Cloudflare وSupabase والتحقق من عمله، ومراجعة الإعدادات المباشرة لـAuth. لا تعتبر تجربة البريد ناجحة دون وصول رسالة وتكملة الرابط.

لم يظهر صندوق مفعّل للدومين في Hostinger. جُهزت مراجعة خطة صندوق واحد لسنة، ثم أُلغي الدفع بناءً على طلب المالك «لا تشترِ الآن». لم يُنشأ صندوق أو تُحفظ بيانات SMTP أو تُغيّر سجلات بريد DNS. إعداد الربط المقترح والاختبارات المتبقية في `docs/email-setup.md`؛ يظل التسجيل مغلقًا.

راجع `docs/operations.md` لخطة النسخ والاستعادة والمراقبة. لا توجد نسخة احتياطية مجدولة أو استعادة سحابية مختبرة حتى توثيق ذلك صراحة.
